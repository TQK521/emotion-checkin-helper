# 8 · 维护升级规范

> 软件交付后，用户随时可能提建议。按本规范处理，保证**旧功能不坏、文档同步更新**。

## 一、反馈处理流程

```
用户提建议 → AI 分析（是否合理/是否新需求）→ 与用户确认改动点
→ 修改代码 → 质量门回归（typecheck/lint/test/build，重点测旧功能没坏）
→ 定版后打包绿色版 → 版本号递增 → 更新文档 → 交付
```

## 二、改动分类与版本号

| 类型 | 例子 | 版本号 |
| --- | --- | --- |
| 修复小问题 | 某处报错、文字错误、小 bug | +0.0.1 |
| 增加小功能 | 加一个导出按钮、一个新页面 | +0.1 |
| 大改版 | 界面重做、核心逻辑更换、技术栈切换 | +1 |

## 三、每次升级必做

1. **质量门回归**：`pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build` 全绿（见《6-测试规范.md》）；
2. **验收**：复用 accept_lib + `_exp_TEMPLATE_accept.py` 分层自检；数据隔离三件套（真实数据哈希前后一致）；
3. **更新文档**：`CHANGELOG.md`（简表）、`docs/jiaojie/00-对话交接总账.md`（详细）、根 `README.md`（如启动/结构变化）、`webapp/README.md`（如命令/目录变化）；
4. **更新版本记录**：日期、版本号、改动内容、修复了什么问题；
5. **数据兼容**：升级后用户旧数据必须还能正常读取；格式变了走 importer 迁移（`src/services/importer`），禁止直接丢弃；
6. **打包时机**：迭代期不打包；仅用户明确"定版/交付"后 `pnpm tauri build` 并更新绿色版交付目录。

## 四、修改记录模板

```
# 修改记录

| 日期 | 版本 | 改动内容 | 修复问题 |
| --- | --- | --- | --- |
| 2026-11-01 | v2.0 | 技术栈切换 webapp（Vue3+TS+Tauri2） | 旧版体积大、路径敏感 |
```

## 五、常见维护诉求与处理

| 用户诉求 | AI 处理 |
| --- | --- |
| "加个功能：……" | 走需求分析 → 开发 → 回归 → 升级 |
| "这里不好用，能不能改" | 确认具体改动点 → 小版本升级 |
| "报错了" | 让用户描述现象/截图 → 先复现后定位（先对照后排除）→ 修复 |
| "数据丢了" | 检查 `%APPDATA%\com.tqk.emotioncheckin\` 备份机制 → 修复并说明找回方式 |
| "绿色版打不开" | 先查路径（是否中文/桌面）→ 复制到纯英文非桌面目录再试 |
