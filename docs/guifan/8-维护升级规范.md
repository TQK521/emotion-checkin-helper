# 8 · 维护升级规范

> 软件交付后，用户随时可能提建议。按本规范处理，保证**旧功能不坏、文档同步更新**。

## 一、反馈处理流程

```
用户提建议 → AI 分析（是否合理/是否新需求）→ 与用户确认改动点
→ 修改代码 → 回归测试（重点测旧功能没坏）→ 重新打包
→ 版本号递增 → 更新使用说明/环境说明 → 交付新 zip
```

## 二、改动分类与版本号

| 类型 | 例子 | 版本号 |
| --- | --- | --- |
| 修复小问题 | 某处闪退、文字错误、小 bug | +0.0.1 |
| 增加小功能 | 加一个导出按钮、一个新选项 | +0.1 |
| 大改版 | 界面重做、核心逻辑更换 | +1 |

## 三、每次升级必做

1. **回归测试**：旧功能全部再走一遍（见《6-测试规范.md》）。
2. **更新文档**：《使用说明》跟着新功能同步改；配置项变了要改《环境配置说明》。
3. **更新《修改记录》**：日期、版本号、改动内容、修复了什么问题。
4. **数据兼容**：升级后用户旧数据（data/、config.json）必须还能正常读取；格式变了要做迁移，禁止直接丢弃。

## 四、修改记录模板

```
# 修改记录

| 日期 | 版本 | 改动内容 | 修复问题 |
| --- | --- | --- | --- |
| 2026-10-18 | v1.0.0 | 首次发布 | - |
| 2026-10-20 | v1.0.1 | 修复XX闪退 | 打开XX时崩溃 |
```

## 五、常见维护诉求与处理

| 用户诉求 | AI 处理 |
| --- | --- |
| "加个功能：……" | 走需求分析 → 开发 → 回归 → 升级 |
| "这里不好用，能不能改" | 确认具体改动点 → 小版本升级 |
| "报错了" | 让用户查看 logs/app.log 或描述现象 → 定位修复 |
| "数据丢了" | 检查 data/ 备份机制 → 修复并说明找回方式 |
