# 5 · 编码与可维护性规范

> 目标：三个月后的 AI 和用户自己，都能快速看懂、安全改动这个程序。

## 一、命名与风格

- 统一命名规则（见《4-项目结构规范.md》）。
- 中英文注释均可，但**关键逻辑必须写注释**：这段代码在做什么、为什么这么做。
- 每个模块/类/重要函数顶部写说明（docstring），一句话讲清用途和入参出参。

## 二、模块化与单一职责

- 一个函数只做一件事；一个文件只装一个模块。
- 界面与逻辑分离：改动按钮位置，不碰核心代码；改核心算法，不碰界面。
- 避免重复代码：相同逻辑抽成公共函数（放 `utils/`）。

## 三、配置与数据

- 所有可调参数进 `config.json`，路径用相对路径或自动获取（`程序目录/`），**禁止硬编码**。
- 用户数据统一存 `data/`，并支持"备份/导出"，防止丢失。

## 四、日志（排查问题的命根子）

- 使用 Python `logging`，写 `logs/app.log`。
- 关键操作记 Info（谁在什么时候做了什么）；出错记 Error（**必须包含完整错误堆栈**）。
- 程序异常时：弹窗提示用户"出错了，请查看 logs 目录下的日志"，而不是静默崩溃。

## 五、错误处理

- 所有可能失败的操作（读文件、连网、类型转换）都要 try/except。
- 给用户友好提示（中文、可操作），不给英文报错堆栈。
- 空输入、文件不存在、路径含中文、重复点击，都必须有兜底。

## 六、版本与记录

- 每次交付附《修改记录》：日期、版本号、改了什么。
- 版本号：修复小问题 +0.0.1；加小功能 +0.1；大改版 +1。
- 使用 Git 管理源码（如用户环境支持）：每次改动一个功能点提交一次，commit 信息写明"改了什么、为什么"。

## 七、安全底线（AI 必守）

- 不收集、不上传任何用户数据；所有数据本地保存。
- 不写破坏性代码（不自动删除用户文件）；清理类操作先备份再提示。
- 生成的代码避免常见漏洞：路径拼接要安全、外部输入要校验。
